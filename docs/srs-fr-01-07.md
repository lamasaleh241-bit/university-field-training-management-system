# SRS — الحسابات والتهيئة (PRD §7.1: FR-01..FR-07 مع FR-04a وFR-06a)

**المنتج:** نظام إدارة التدريب الميداني الجامعي
**النطاق:** متطلبات النظام التفصيلية المستمدة من FR-01 إلى FR-07 وFR-04a وFR-06a، وقواعد العمل BR-01 إلى BR-26 ذات الصلة.
**لغة الوثيقة:** عربية تقنية مع المصطلحات الإنجليزية عند الحاجة.
**مصادر الحقيقة وترتيب الأولوية:** `PRD.md` ثم `docs/user-flow.md` ثم `docs/technical-design.md`. عند تعارضها، يحكم PRD؛ لا يُفسر صمت المصدر الأعلى على أنه اعتماد لتفصيل أدنى أولوية.

## 1. اصطلاحات التتبع

- **SRS-01..SRS-09:** متطلبات النظام التفصيلية. SRS-08 يقابل FR-04a، وSRS-09 يقابل FR-06a مع قاعدة UTC في BR-25.
- **AC-xx:** معيار قبول مرتبط بمتطلب SRS.
- **BR-xx:** يحافظ على رقم قاعدة العمل في PRD §8 مع بادئة موحدة؛ مثال: قاعدة PRD رقم 2 تصبح BR-02.
- **Proposed:** تفصيل تقني غير محدد بالمصادر، وليس قرارًا معتمدًا أو سلوكًا مطلوبًا. لا يجوز تحويله إلى التزام تنفيذ قبل اعتماده.
- لا تحدد هذه الوثيقة HTTP status codes أو ضمانات idempotency/concurrency جديدة. إذا احتاج التنفيذ إليها، فهي بحاجة اقتراح واعتماد مستقل.

## 2. قواعد العمل BR-01..BR-26

| المعرّف | قاعدة PRD §8 | علاقتها بنطاق SRS |
|---|---|---|
| BR-01 | لكل كلية إعداداتها وبياناتها المستقلة. | ذات صلة بـSRS-02 وSRS-03 وSRS-06 وSRS-07 ضمن نطاق الكلية. |
| BR-02 | لا تفعّل حسابات الطالب أو المشرف أو مسؤول الشركة قبل موافقة مسؤول الكلية. | حاكمة لـSRS-01 وSRS-04. |
| BR-03 | يراجع طلب التدريب بالترتيب: مسؤول الشركة، ثم مسؤول الكلية للاعتماد النهائي. | خارج نطاق FR-01..FR-07. |
| BR-04 | للطالب طلب نشط واحد في الوقت نفسه؛ إلغاؤه متاح قبل الاعتماد النهائي. | خارج نطاق FR-01..FR-07. |
| BR-05 | رفض الشركة ينهي الطلب الحالي مع تسجيل السبب. إمكانية إعادة التقديم على الفرصة نفسها قرار للشركة. | خارج نطاق FR-01..FR-07. |
| BR-06 | تحدد الكلية الحد الأدنى للساعات ومدة التدريب وساعات العمل اليومية بحسب التخصص. | حاكمة لـSRS-07. |
| BR-07 | ساعات اليوم = وقت الانصراف − وقت الحضور للسجل المعتمد؛ لا تخصم الاستراحات في الـMVP. | خارج النطاق. |
| BR-08 | إذا تجاوزت الساعات الحد اليومي المحدد للتخصص، تُحتسب حتى الحد فقط. | خارج النطاق. |
| BR-09 | سجل الحضور دون انصراف يوسم «غير مكتمل» ولا يحتسب حتى تصحيحه بطلب من الطالب واعتماده. | خارج النطاق. |
| BR-10 | الاعتماد اليومي للحضور مسؤولية مسؤول جهة التدريب. | خارج النطاق. |
| BR-11 | يطلب الموقع وقت التسجيل فقط، وبإذن أثناء الاستخدام؛ لا يُتتبع موقع الطالب باستمرار. | خارج النطاق. |
| BR-12 | نصف قطر الموقع الافتراضي 150 مترًا ويحدده مسؤول الكلية لكل موقع، مع قابلية التعديل. | خارج النطاق. |
| BR-13 | إذا ساءت دقة GPS عن 100 متر أو كان الطالب خارج النطاق، فلا اعتماد تلقائي، ويتاح طلب استثناء. | خارج النطاق. |
| BR-14 | تتطلب المواقع الجديدة موافقة مسؤول الكلية قبل استخدامها للتحقق من الحضور. | خارج النطاق. |
| BR-15 | لا تُضاف ساعات العطل تلقائيًا؛ تُحتسب فقط عند وجود سجل فعلي معتمد، وتوسم كعمل استثنائي. | خارج النطاق. |
| BR-16 | لا يُعتمد سجل تصحيح أو استثناء قبل مراجعة مسؤول الشركة. | خارج النطاق. |
| BR-17 | لا يوجد وضع حضور دون اتصال في الـMVP، ولا يظهر الطلب مقدمًا إذا لم يصل للخادم. | خارج النطاق. |
| BR-18 | التقييم النهائي وصفي، يقدمه مسؤول الشركة مرة واحدة، وهو شرط الإغلاق الطبيعي للتدريب المكتمل. | خارج النطاق. |
| BR-19 | يستطيع مسؤول الكلية استثناء شرط التقييم وإغلاق التدريب دون تقييم عند تعذر تقديمه، بشرط توثيق الاستثناء. | خارج النطاق. |
| BR-20 | يستطيع مسؤول الكلية إنهاء التدريب استثناءً بناءً على طلب رسمي موثق من الطالب أو جهة التدريب؛ ولا يملك صلاحية الإنهاء الاعتباطي وفق القرارات الحالية. | خارج النطاق. |
| BR-21 | الطلب الرسمي هو طلب مكتوب يُقدَّم داخل النظام من الطالب أو جهة التدريب، يتضمن السبب، ويمكن إرفاق مستند اختياريًا، ويُحفظ مع القرار. | خارج نطاق FR-01..FR-07. |
| BR-22 | لا يرى مسؤول الشركة ملاحظات المشرف الأكاديمي أو المداولات والقرارات الداخلية للكلية. | خارج النطاق. |
| BR-23 | لا يطّلع مسؤول الكلية على المحادثات إلا عند نزاع أو طلب رسمي، مع تسجيل السبب والوقت والهوية. | خارج النطاق. |
| BR-24 | المسؤول الأعلى يدير إضافة الكليات، ولا يطّلع افتراضيًا على سجلات التدريب أو المحادثات أو التقييمات. | حاكمة لـSRS-06 وحدود الوصول المرتبطة به. |
| BR-25 | تُخزَّن الأوقات بتوقيت UTC، ويُحتسب التاريخ المحلي لسجل الحضور بحسب المنطقة الزمنية الإلزامية للكلية. | حاكمة لـSRS-09. |
| BR-26 | الاسم الأول والاسم الأخير إلزاميان لكل المستخدمين؛ الرقم الجامعي إلزامي للطالب؛ واسم الشركة إلزامي لمسؤول جهة التدريب. | حاكمة لـSRS-08. |

## 3. متطلبات النظام التفصيلية

### SRS-01 — التسجيل الذاتي للأدوار المحددة

**التتبّع:** `SRS-01 -> PRD FR-01 -> BR-02`.

**السلوك:**

- **Preconditions:** يباشر شخص غير مسجل تدفق إنشاء حساب ذاتي. الأنواع التي يتيحها التسجيل الذاتي في هذا المتطلب هي الطالب والمشرف الأكاديمي ومسؤول جهة التدريب فقط.
- **Inputs:** نوع الحساب، البريد الإلكتروني، كلمة المرور، والبيانات/الاختيارات الأخرى التي تحددها المتطلبات التابعة FR-02..FR-04. لا يُفترض هنا حقل إضافي غير منصوص عليه في PRD.
- **Validation:** يجب أن يكون الدور المختار من الأدوار الثلاثة المحددة؛ قواعد كلمة المرور والتحقق من البريد والتفعيل مفصلة في SRS-04 وSRS-05. لا تحدد PRD قيود تفرد البريد أو شكل التحقق beyond وجوب التحقق من البريد.
- **State changes:** إنشاء الحساب وحده لا يفعّله؛ يظل غير مفعل إلى أن تتحقق متطلبات SRS-04 وموافقة مسؤول الكلية وفق BR-02.
- **System response:** يتيح النظام التسجيل الذاتي لهذه الأنواع، ويوجه المستخدم لمسار التحقق ثم طلب التفعيل. لا يتيح هذا المتطلب التسجيل الذاتي لمسؤول الكلية أو المسؤول الأعلى.

**الأخطاء والحواف:**

- `docs/user-flow.md` يحدد عند نقص الحقول: «أكمل الحقول المطلوبة.»
- ويحدد في مسار الطالب عند تعذر إرسال/التحقق من البريد: «تعذر إرسال رسالة التحقق. حاول مرة أخرى.»
- رسالة بريد غير صالح أو مستخدم موصوفة بأنها رسالة حقل مناسبة؛ لا يحدد المصدر نصًا حرفيًا بعينه، كما لا يحدد سلوك تكرار التسجيل المتزامن.
- **Proposed — HTTP:** لا يحدد أي مصدر HTTP status code لهذه الحالات؛ لا يُسند code في هذه الوثيقة.
- **Proposed — idempotency/concurrency:** لا تحدد المصادر سلوك إعادة إرسال إنشاء الحساب أو سباق التسجيل بالبريد نفسه؛ لا يُفترض إنشاء واحد/استجابة موحدة دون قرار.

**معايير القبول:**

- **AC-01-Happy:** Given زائر يختار أحد الأدوار الثلاثة المسموح بها ويدخل المدخلات المطلوبة، When يرسل نموذج التسجيل بمدخلات مقبولة، Then ينشئ النظام حسابًا ضمن تدفق التسجيل، ولا يعتبره مفعّلًا قبل استكمال تحقق البريد وموافقة مسؤول الكلية.
- **Validation failure — Open Question:** لا يحدد PRD قواعد تحقق البريد والتكرار الكاملة أو حقلًا حرفيًا ورسالة موحدة لكل دور؛ يحدد `user-flow.md` رسائل لبعض حالات الطالب فقط. يلزم تحديد تغطية رسائل التحقق لبقية الدورين قبل اعتماد AC سلبي شامل.

### SRS-02 — اختيار كلية من الكليات المتاحة أثناء التسجيل

**التتبّع:** `SRS-02 -> PRD FR-02 -> BR-01, BR-02`.

**السلوك:**

- **Preconditions:** المستخدم داخل تدفق التسجيل الذاتي لأحد الأدوار التي يغطيها FR-01.
- **Inputs:** اختيار كلية من قائمة الكليات المتاحة التي يعرضها النظام.
- **Validation:** يجب أن يكون الاختيار كلية متاحة في القائمة؛ لا يحدد PRD تعريف «متاحة» أو سياسة حالة الكلية. يعامل الاختيار غير المتاح وفق رسالة المصدر أدناه، من دون اختراع سياسة إضافية.
- **State changes:** يرتبط طلب/حساب التسجيل بالكلية المختارة؛ بيانات كل كلية وإعداداتها مستقلة وفق BR-01. ولا ينتج عن الاختيار تفعيل الحساب؛ BR-02 يحكم التفعيل.
- **System response:** يعرض النظام قائمة اختيار الكلية أثناء التسجيل.

**الأخطاء والحواف:**

- `docs/user-flow.md`: عند عدم توفر كلية/تخصص: «منع الإرسال وإظهار أن الخيار غير متاح.» هذه صياغة سلوكية وليست نص واجهة محددًا.
- لا تحدد المصادر رسالة حالة القائمة الفارغة أو سبب عدم توفر كلية بعينها.
- **Proposed — HTTP:** لا يحدد HTTP status code.
- **Proposed — idempotency/concurrency:** لا تحدد المصادر التعامل مع تغيّر إتاحة الكلية بعد عرض القائمة وقبل الإرسال.

**معايير القبول:**

- **AC-02-Happy:** Given قائمة كليات متاحة في تدفق التسجيل، When يختار المتقدم كلية ويرسل التسجيل، Then يستخدم النظام الكلية المختارة كنطاق للحساب/طلب التفعيل، مع بقاء بيانات الكليات مستقلة وعدم تفعيل الحساب قبل موافقة مسؤول تلك الكلية.
- **Validation failure — Open Question:** لا يوجد في المصادر وصف لمسار القائمة الفارغة أو آلية تحديث القائمة إذا تغيرت إتاحة الكلية أثناء التسجيل.

### SRS-03 — اختيار الطالب تخصصًا من قائمة تخصصات كليته

**التتبّع:** `SRS-03 -> PRD FR-03 -> BR-01, BR-06`.

**السلوك:**

- **Preconditions:** المتقدم يختار دور الطالب، واختار كلية ضمن SRS-02.
- **Inputs:** تخصص من قائمة التخصصات التي تديرها الكلية المختارة.
- **Validation:** يجب أن يكون التخصص ضمن قائمة تخصصات الكلية. لا تحدد PRD قواعد حالة التخصص أو سلوك تغير القائمة أثناء التسجيل.
- **State changes:** يرتبط اختيار التخصص بحساب الطالب لكي تُطبّق متطلبات التدريب المناسبة لتخصصه وفق قصة المستخدم وBR-06. لا تعد هذه العملية اعتمادًا لحساب الطالب.
- **System response:** يعرض النظام تخصصات الكلية المحددة للطالب؛ لا ينطبق اختيار التخصص على تسجيل المشرف أو مسؤول جهة التدريب بحسب FR-03.

**الأخطاء والحواف:**

- `docs/user-flow.md`: عند عدم توفر الكلية/التخصص، يمنع الإرسال ويظهر أن الخيار غير متاح.
- لا تحدد المصادر نص الرسالة الحرفي أو كيفية التعامل مع كلية بلا تخصصات متاحة.
- **Proposed — HTTP:** لا يحدد HTTP status code.
- **Proposed — idempotency/concurrency:** لا تحدد المصادر سلوك تغير ارتباط التخصص بالكلية بين العرض والحفظ.

**معايير القبول:**

- **AC-03-Happy:** Given متقدم بدور الطالب وكلية مختارة لها تخصصات مدارة، When يختار تخصصًا من القائمة ويرسل التسجيل، Then يرتبط التخصص المختار بحساب الطالب ويكون متاحًا لتطبيق متطلبات التخصص وفق BR-06، ويبقى الحساب غير مفعل حتى موافقة مسؤول الكلية.
- **Validation failure — Open Question:** لا تحدد المصادر ماذا يحدث إذا لم تكن للكلية تخصصات متاحة أو عُطّل التخصص بعد عرضه وقبل إرسال التسجيل.

### SRS-04 — بيانات المصادقة والتحقق من البريد ومسار التفعيل

**التتبّع:** `SRS-04 -> PRD FR-04 -> BR-02`.

**السلوك:**

- **Preconditions:** المستخدم يباشر التسجيل الذاتي في أحد الأدوار الثلاثة في FR-01، واختار كلية؛ الطالب يختار تخصصًا وفق FR-03.
- **Inputs:** بريد إلكتروني وكلمة مرور. الحقول الأخرى التي حسمها PRD ضمن FR-02/FR-03 تُعامل في المتطلبات التابعة.
- **Validation:** يلزم التحقق من البريد قبل إرسال طلب تفعيل الحساب إلى مسؤول الكلية. لا يصبح الحساب مفعّلًا قبل موافقة المسؤول. الحد الأدنى لطول كلمة المرور ووظيفة استعادتها وقفل الدخول موثقة منفصلًا في SRS-05.
- **State changes:** تدفق الحساب ينتقل من تسجيل غير مكتمل إلى بريد متحقق، ثم طلب تفعيل مرسل/بانتظار قرار مسؤول الكلية، ثم لا ينتقل إلى حالة مفعّلة إلا بموافقة مسؤول الكلية. لا تحدد PRD قيم enum تقنية للحالات.
- **System response:** بعد تحقق البريد، يرسل النظام طلب تفعيل الحساب لمسؤول التدريب في الكلية، ويعرض للمستخدم حالة الانتظار. لا يستطيع الحساب غير المفعّل استخدام وظائف الدور المحمية حسب PRD §11.1.

**الأخطاء والحواف:**

- `docs/user-flow.md` للطالب: «تعذر إرسال رسالة التحقق. حاول مرة أخرى.»
- عند اكتمال التحقق وانتظار الموافقة: «تم التحقق من بريدك. حسابك بانتظار موافقة مسؤول الكلية.»
- نقص البيانات: «أكمل الحقول المطلوبة.»
- كلية/تخصص غير متاح: منع الإرسال وإظهار أن الخيار غير متاح.
- user-flow يذكر أن مسؤول الكلية يوافق أو يرفض في مسارات التسجيل، لكن PRD FR-04 يحدد عدم التفعيل قبل الموافقة ولا يفصل أثر الرفض أو رسالة رفض الحساب؛ يُسجل هذا كفجوة لا كحالة مفصلة.
- **Proposed — HTTP:** لا يحدد المصدر status codes لطلب التحقق أو التفعيل.
- **Proposed — idempotency/concurrency:** لا تحدد المصادر إعادة إرسال رسالة التحقق أو تكرار طلب التفعيل أو التزامن بين قرار التفعيل وإعادة الإرسال.

**معايير القبول:**

- **AC-04-Happy:** Given مستخدم أكمل التسجيل وأثبت ملكية بريده، When يكتمل تحقق البريد، Then يرسل النظام طلب التفعيل إلى مسؤول الكلية المختارة ويعرض أن الحساب بانتظار موافقته؛ يظل الحساب غير مفعل إلى أن يوافق المسؤول.
- **Validation failure:** Given بريد لم يكتمل التحقق منه، When يحاول المستخدم إكمال خطوة إرسال طلب التفعيل، Then لا يرسل النظام طلب التفعيل قبل تحقق البريد. النص الحرفي لحالة «بريد لم يتحقق» غير محدد في PRD أو user-flow؛ **Open Question** لرسالة الواجهة ومسار إعادة الإرسال.
- **Edge — Open Question:** لا تحدد المصادر حالة الحساب والرسالة النهائية ومسار الاعتراض بعد رفض مسؤول الكلية.

### SRS-05 — الحد الأدنى لكلمة المرور واستعادتها وقفل الدخول

**التتبّع:** `SRS-05 -> PRD FR-05 -> BR-02` (صلة BR-02 فقط تخص الفصل بين المصادقة وتفعيل الحساب؛ قواعد كلمة المرور والقفل نصها FR-05).

**السلوك:**

- **Preconditions:** عند إنشاء كلمة مرور أو استخدام تسجيل الدخول/استعادة كلمة المرور.
- **Inputs:** كلمة مرور عند التسجيل/تغييرها وفق المسار الذي توفره وظيفة الاستعادة، ومحاولات تسجيل الدخول.
- **Validation:** لا تقل كلمة المرور عن 8 خانات. تتوفر وظيفة «نسيت كلمة المرور». بعد 5 محاولات دخول فاشلة متتالية يُقفل تسجيل الدخول 15 دقيقة.
- **State changes:** بعد بلوغ خمس محاولات فاشلة متتالية، حالة تسجيل الدخول تكون مقفلة لمدة 15 دقيقة؛ لا تحدد المصادر تفاصيل عداد المحاولات أو تصفيره أو تفاعل النجاح/الاستعادة مع القفل.
- **System response:** يرفض تسجيل الدخول خلال القفل ويبين وقت/مدة الانتظار وفق user-flow. يتيح النظام وظيفة استعادة كلمة المرور، دون أن يحدد PRD خطواتها.

**الأخطاء والحواف:**

- كلمة مرور أقصر من 8 خانات: «يجب ألا يقل طول كلمة المرور عن 8 خانات.»
- بعد 5 محاولات دخول فاشلة متتالية: يقفل الدخول 15 دقيقة ويظهر وقت/مدة الانتظار؛ لا يوجد نص حرفي نهائي للرسالة.
- **Open Question:** لم تحدد المصادر حالات الحد الزمني بالضبط، إعادة تصفير العداد، تسجيل الدخول أثناء القفل، أو تفاصيل استعادة كلمة المرور ورسائلها.
- **Proposed — HTTP:** لا يحدد المصدر status codes لرفض كلمة المرور أو القفل أو استعادة كلمة المرور.
- **Proposed — idempotency/concurrency:** لا تحدد المصادر التزامن بين محاولات تسجيل الدخول المتوازية أو طلبات الاستعادة المتكررة؛ لا يُعتمد ترتيب أو عداد ذري ضمن هذا SRS.

**معايير القبول:**

- **AC-05-Happy:** Given كلمة مرور طولها 8 خانات على الأقل، When يسجل المستخدم دخولًا ببيانات صحيحة وحساب مخول، Then يقبل النظام محاولة الدخول ما لم يكن الحساب داخل فترة قفل قائمة.
- **AC-05-Validation:** Given كلمة مرور أقصر من 8 خانات في نموذج التسجيل، When يحاول المستخدم إرسال النموذج، Then يرفضها النظام ويعرض «يجب ألا يقل طول كلمة المرور عن 8 خانات.»
- **AC-05-Edge:** Given 5 محاولات دخول فاشلة متتالية، When تبدأ المحاولة التالية ضمن قيد القفل، Then يكون تسجيل الدخول مقفلًا 15 دقيقة ويعرض النظام وقت/مدة الانتظار. تفاصيل الحد الفاصل بعد انتهاء المدة **Open Question**.
- **AC-05-Open:** وظيفة «نسيت كلمة المرور» مطلوبة، لكن شروطها وخطواتها ورسائلها ونتيجة إعادة تعيين كلمة المرور غير موصوفة؛ يلزم تحديدها قبل صياغة سيناريو قبول تفصيلي لها.

### SRS-06 — إضافة كلية بواسطة المسؤول الأعلى

**التتبّع:** `SRS-06 -> PRD FR-06 -> BR-01, BR-24`؛ ومتطلبات المنطقة الزمنية في SRS-09.

**السلوك:**

- **Preconditions:** المستخدم المسؤول الأعلى مخول بإدارة إضافة الكليات. لا يملك مسؤول الكلية هذه الصلاحية. PRD §9 وBR-24 يحصران المسؤول الأعلى في إدارة إضافة الكليات ضمن هذا السياق، مع منع الاطلاع الافتراضي على سجلات التدريب والمحادثات والتقييمات.
- **Inputs:** معلومات تعريف الكلية، وتشمل المنطقة الزمنية الصالحة التي يحددها المسؤول الأعلى وفق FR-06a وSRS-09.
- **Validation:** لا ينشئ النظام كلية دون منطقة زمنية صالحة. لا يحدد PRD بقية الحقول الإلزامية أو قواعد تفرد/صلاحية اسم الكلية أو حالة الكلية عند الإنشاء.
- **State changes:** إضافة كلية جديدة ضمن النظام، مع استقلال إعداداتها وبياناتها وفق BR-01. لا تحدد PRD نتيجة إنشاء الكلية بالنسبة إلى ظهورها في قائمة التسجيل أو حالة تفعيلها.
- **System response:** يمنح النظام وظيفة إضافة كلية للمسؤول الأعلى فقط؛ يمنع استخدامها من مسؤول الكلية. لا يجوز أن تمنح إضافة الكلية للمسؤول الأعلى وصولًا افتراضيًا إلى سجلات التدريب أو المحادثات أو التقييمات.

**الأخطاء والحواف:**

- `docs/user-flow.md` يحدد للحقول الناقصة: يمنع الحفظ ويحدد الحقل، لكن هذه الحقول مفترضة في user-flow وليست جميعها منصوصًا عليها في PRD.
- user-flow: منطقة زمنية غير صالحة تعرض «اختر منطقة زمنية صالحة.»
- user-flow: تعذر الحفظ يعرض «تعذر إنشاء الكلية. لم يتم تأكيد الحفظ؛ حاول مرة أخرى.»
- لا يحدد PRD رسالة محاولة مسؤول كلية إضافة كلية أو قائمة الكليات الفارغة/التكرار.
- **Proposed — HTTP:** لا يحدد المصدر status codes لنجاح/رفض/فشل إضافة الكلية.
- **Proposed — idempotency/concurrency:** لا تحدد المصادر منع الكليات المكررة أو سلوك إعادة إرسال عملية الإنشاء بعد timeout.

**معايير القبول:**

- **AC-06-Happy:** Given مستخدمًا بدور المسؤول الأعلى، When ينفذ إضافة كلية، Then يضيف النظام كلية مستقلة الإعدادات والبيانات ويقصر وظيفة الإضافة على المسؤول الأعلى، من دون منح وصول افتراضي إلى بيانات التدريب أو المحادثات أو التقييمات.
- **AC-06-Authorization:** Given مستخدمًا بدور مسؤول الكلية، When يحاول إضافة كلية، Then لا يمنحه النظام هذه الصلاحية وفق FR-06. لا تحدد المصادر رسالة المنع أو طريقة عرضها؛ **Open Question**.
- **AC-06-Validation:** Given المسؤول الأعلى ترك المنطقة الزمنية فارغة أو أدخل قيمة غير صالحة، When يحاول إنشاء الكلية، Then يمنع النظام الإنشاء؛ وعند عدم صلاحية المنطقة يعرض «اختر منطقة زمنية صالحة.»
- **Open Question:** بقية حقول إنشاء الكلية وقواعد التكرار/ظهورها غير محددة في PRD.

### SRS-07 — إدارة متطلبات التدريب بحسب التخصص

**التتبّع:** `SRS-07 -> PRD FR-07 -> BR-01, BR-06`.

**السلوك:**

- **Preconditions:** مسؤول التدريب في كلية يدير إعدادات كليته وتخصصاتها؛ لا يمتد الوصول إلى كلية أخرى وفق استقلال الكليات BR-01.
- **Inputs:** لكل تخصص، القيم الثلاث التالية التي تسميها FR-07 وBR-06: الحد الأدنى لإجمالي الساعات، مدة التدريب، وساعات العمل اليومية.
- **Validation:** القيم تتعلق بالتخصص الذي تديره الكلية. لا تحدد PRD الوحدات التقنية أو الحد الأدنى/الأقصى لكل قيمة أو سياسة السماح بقيمة صفرية أو سالبة أو كسور أو قيم فارغة.
- **State changes:** ينشئ/يعدّل مسؤول الكلية إعدادات متطلبات التدريب بحسب التخصص؛ لا تحدد FR-07 تاريخ سريان التعديل أو هل يسري على التدريبات الجارية.
- **System response:** تستخدم المتطلبات لتمثيل الحد الأدنى لإجمالي الساعات ومدة التدريب وساعات العمل اليومية وفق تخصص الطالب وإعدادات كليته. لا يحدد هذا المتطلب حساب التقدم أو سلوك النسخ التاريخية.

**الأخطاء والحواف:**

- `docs/user-flow.md` يقول عند نقص الإعدادات: «يمنع اعتمادها أو يوضح الحقول الناقصة.» لا يوجد نص رسالة حرفي محدد.
- لا تحدد PRD سلوك تعديل المتطلبات بعد بدء تدريب أو قيمة خارج النطاق أو تخصص بلا متطلبات.
- **Proposed — HTTP:** لا يحدد المصدر status codes لعمليات قراءة/إنشاء/تعديل المتطلبات.
- **Proposed — idempotency/concurrency:** لا تحدد المصادر آلية التعامل مع حفظ تعديلات متزامنة أو نسخ الإعدادات عند تغييرها.

**معايير القبول:**

- **AC-07-Happy:** Given مسؤول كلية مخولًا وتخصصًا ضمن كليته، When يحفظ متطلبات التخصص متضمنة الحد الأدنى لإجمالي الساعات ومدة التدريب وساعات العمل اليومية، Then يحفظ النظام القيم لهذا التخصص/الكلية لتستخدم متطلبات التدريب بحسب تخصص الطالب وإعدادات كليته.
- **Validation failure — Open Question:** لا تحدد المصادر نطاقات القيم أو وحداتها أو سياسة القيم غير الموجبة/الفارغة؛ لذلك لا يوضع Given/When/Then تحقق رقمي مخترع.
- **Edge — Open Question:** يتعين حسم تطبيق التغيير على تدريب جارٍ أو على دفعات جديدة فقط؛ وهذا سؤال PRD §17 رقم 7، ولا يُحل هنا.

### SRS-08 — حقول الهوية الإلزامية عند التسجيل

**التتبّع:** `SRS-08 -> PRD FR-04a -> BR-26`.

**السلوك:**

- **Preconditions:** يرسل المستخدم نموذج التسجيل الذاتي لأحد الأدوار المشمولة في FR-01.
- **Inputs:** الاسم الأول والاسم الأخير لجميع المستخدمين؛ الرقم الجامعي للطالب؛ واسم الشركة لمسؤول جهة التدريب.
- **Validation:** يمنع النظام إرسال النموذج إذا غاب أي حقل إلزامي ينطبق على الدور المختار. لا يحدد PRD صيغة أو طولًا لهذه الحقول، ولا قاعدة تفرد الرقم الجامعي.
- **State changes:** لا يُرسل نموذج التسجيل الناقص؛ وعند اكتمال الحقول يستمر التسجيل وفق SRS-01 وSRS-04.
- **System response:** يحدد النظام الحقل المطلوب استكماله؛ الرسالة المحددة في `user-flow.md`: «أكمل الحقول المطلوبة.»

**الأخطاء والحواف:** لا يحدد المصدر قاعدة تفرد الرقم الجامعي أو صحته لدى الجامعة/الكلية؛ وهي أسئلة PRD §17 رقم 19. ولا يعتمد حقولًا أخرى مثل الهاتف؛ PRD §17 رقم 20 يسأل عنها ولا يحسمها.

**معايير القبول:**

- **AC-08-Happy:** Given مستخدم أدخل الاسم الأول والأخير، وأدخل الرقم الجامعي إذا كان طالبًا أو اسم الشركة إذا كان مسؤول جهة تدريب، When يرسل نموذج التسجيل، Then يسمح النظام بمتابعة بقية خطوات التسجيل.
- **AC-08-Validation:** Given غياب حقل إلزامي ينطبق على الدور، When يحاول المستخدم إرسال نموذج التسجيل، Then يمنع النظام الإرسال ويعرض «أكمل الحقول المطلوبة.»
- **Open Question:** لا يختبر هذا المعيار تفرد الرقم الجامعي أو التحقق منه إلى أن تحسم PRD §17 رقم 19.

### SRS-09 — المنطقة الزمنية للكلية وتاريخ الحضور المحلي

**التتبّع:** `SRS-09 -> PRD FR-06a -> BR-25`؛ وإضافة الكلية في `PRD FR-06`.

**السلوك:**

- **Preconditions:** المسؤول الأعلى يضيف كلية جديدة، أو يعالج النظام أوقات سجل حضور مرتبط بكلية لها منطقة زمنية محددة.
- **Inputs:** منطقة زمنية صالحة يحددها المسؤول الأعلى عند إضافة الكلية، وأوقات السجل.
- **Validation:** لا تُنشأ كلية دون منطقة زمنية صالحة. لا يحدد PRD صيغة/قائمة المناطق الزمنية المقبولة.
- **State changes:** تخزن الأوقات بتوقيت UTC؛ ويُحتسب التاريخ المحلي لسجل الحضور بحسب منطقة الكلية. لا يحدد المتطلب أثر تغيير المنطقة الزمنية لاحقًا على السجلات التاريخية.
- **System response:** يرفض النظام إنشاء الكلية عند غياب المنطقة الزمنية أو عدم صلاحيتها؛ ويستخدم منطقة الكلية لاشتقاق تاريخ سجل الحضور مع بقاء التوقيتات UTC.

**الأخطاء والحواف:** `user-flow.md` يحدد للقيمة غير الصالحة: «اختر منطقة زمنية صالحة.» ولفشل حفظ الكلية: «تعذر إنشاء الكلية. لم يتم تأكيد الحفظ؛ حاول مرة أخرى.» أثر تغيير timezone لاحقًا سؤال PRD §17 رقم 22، وظهور الكلية في قائمة التسجيل سؤال رقم 18.

**معايير القبول:**

- **AC-09-Happy:** Given المسؤول الأعلى يضيف كلية بمنطقة زمنية صالحة، When ينشئ الكلية، Then تحفظ المنطقة الزمنية إلزاميًا. Given وقت حضور/انصراف مرتبط بالكلية، When يحتسب النظام تاريخ سجل الحضور، Then يستخدم timezone الكلية مع استمرار تخزين التوقيت UTC.
- **AC-09-Validation:** Given المنطقة الزمنية فارغة أو غير صالحة، When يحاول المسؤول الأعلى إنشاء الكلية، Then يمنع النظام الإنشاء؛ وعند عدم صلاحية القيمة يعرض «اختر منطقة زمنية صالحة.»
- **AC-09-Timezone:** Given وقت UTC يقع عند حد يختلف فيه التاريخ المحلي عن تاريخ UTC، When يحتسب النظام تاريخ الحضور، Then يعتمد التاريخ المحلي للكلية.
- **Open Question:** لا يحسم SRS تغيير timezone بعد الإنشاء أو أثره على سجلات الحضور السابقة؛ راجع PRD §17 رقم 22.

## 4. Conflicts

لا يوجد نص صريح في PRD يناقض مباشرة الوظائف الأساسية FR-01..FR-07 كما صيغت. توجد مع ذلك فروق/تفاصيل أدنى أولوية لا يجوز ترقية تفاصيلها إلى متطلبات دون قرار:

1. **حقول الهوية:** حُسمت في PRD FR-04a وBR-26 ومعيار القبول 38؛ تتسق مع `user-flow.md` و`technical-design.md`. تبقى قيود تفرد/التحقق من الرقم الجامعي سؤالًا مفتوحًا في PRD §17 رقم 19.
2. **المنطقة الزمنية:** حُسم إلزامها عند إضافة كلية وتخزين الأوقات UTC واحتساب تاريخ الحضور بتوقيت الكلية في PRD FR-06a وBR-25 ومعايير القبول 39-40؛ تتسق مع `user-flow.md` و`technical-design.md`. تبقى آلية تغييرها لاحقًا وأثر ذلك على السجلات السابقة مفتوحة في PRD §17 رقم 22.
3. **استقلال النطاق مقابل آلية العزل — PRD BR-01/BR-24 مقابل technical-design §2.4:** PRD يحدد استقلال بيانات الكليات وحدود الاطلاع، بينما technical-design يحدد PostgreSQL/RLS وآلية `college_id`. هذا تفصيل تنفيذ لا تعارض وظيفي؛ لا يضيف هذا SRS آلية قاعدة بيانات إلى متطلبات FR-01..FR-07.
4. **رفض تفعيل الحساب — PRD FR-04 مقابل user-flow §11.1 وPRD §11.1:** PRD ينص على عدم التفعيل قبل موافقة مسؤول الكلية، بينما user-flow يذكر الموافقة أو الرفض، ولا يحدد PRD أثر الرفض أو حالة الحساب الناتجة. لا يوجد تناقض في أصل سلطة المراجعة، لكن نتيجة الرفض غير محددة؛ لا تُضاف حالة/رسالة رفض إلى SRS.
5. **حالة ظهور الكلية بعد إنشائها — PRD FR-06 مقابل user-flow §5.1:** user-flow يقول إن الكلية تصبح متاحة في قائمة التسجيل وفق حالة تفعيلها، بينما PRD لا يحدد حالة كلية أو متى تصبح متاحة. هذا تفصيل غير محسوم وليس متطلبًا معتمدًا.

## 6. أسئلة PRD §17 المحمولة ذات الصلة بهذا النطاق

لا تُحل الأسئلة التالية في هذه الوثيقة:

- **PRD §17 رقم 7 — التخصص والمتطلبات:** هل يمكن تغيير متطلبات التخصص بعد بدء التدريب؟ وإذا تغيرت، هل تطبق على التدريب الجاري أم على الدفعات الجديدة فقط؟ يؤثر في SRS-07/FR-07.
- **PRD §17 رقم 12 و21 — إدارة الحسابات/الحساب المرفوض:** ما مسار رفض حساب أو تعطيله لاحقًا؟ وهل يمكن للمستخدم الانضمام لأكثر من كلية أو لمسؤول الشركة إدارة عدة جهات/فروع؟ وما حالة الحساب المرفوض وإمكانية إعادة التسجيل أو الاعتراض؟ يؤثر في SRS-01 وSRS-02 وSRS-04 وSRS-08.
- **PRD §17 رقم 15 — المتطلبات غير الوظيفية:** ما أهداف الأداء والتوافر والاستعادة والنسخ الاحتياطي ومتطلبات أمن المعلومات الأخرى؟
- **PRD §17 رقم 17 — اللغات وإمكانية الوصول:** هل يلزم دعم الإنجليزية أو معايير إتاحة محددة؟ العربية معتمدة في PRD؛ التفاصيل الإضافية غير محسومة.
- **PRD §17 رقم 18 — ظهور الكلية الجديدة:** متى تصبح متاحة في قائمة التسجيل بعد إضافتها؟ وهل لها حالة مفعّلة/موقوفة؟ يؤثر في SRS-02 وSRS-06 وSRS-09.
- **PRD §17 رقم 19 — الرقم الجامعي:** هل يجب أن يكون فريدًا؟ وهل تتحقق الكلية منه أو من التخصص المختار؟ يؤثر في SRS-08.
- **PRD §17 رقم 20 — حقول إضافية:** هل يلزم حقل الهاتف أو أي حقل آخر للتسجيل؟ لا تضاف حقول قبل الحسم؛ يؤثر في SRS-01 وSRS-08.
- **PRD §17 رقم 22 — المنطقة الزمنية:** هل يمكن تغييرها بعد إنشاء الكلية، وما أثر ذلك على سجلات الحضور السابقة؟ يؤثر في SRS-09.

## 7. Open Questions إضافية داخل حدود FR-01..FR-07

1. ما تعريف «الكليات المتاحة» و«تخصصات الكلية» في واجهة التسجيل، وما السلوك عند خلو القوائم أو تغيّر الإتاحة أثناء التسجيل؟
2. ما خطوات ورسائل استعادة كلمة المرور وإعادة إرسال إثبات البريد، وما أثر رفض طلب التفعيل؟
3. ما الوحدات والنطاقات المسموحة لقيم متطلبات التدريب الثلاثة، وكيف تتصرف المنظومة عند تعديل متطلبات تخصص مستخدم في تدريب جارٍ؟
4. ما رسائل الرفض الموحدة ونطاق HTTP status codes، وما سلوك idempotency/concurrency للعمليات التي لم تحددها المصادر؟ هذه البنود غير معتمدة؛ أي اقتراح لاحق يجب وسمه Proposed ومراجعته.
