# جرد الشاشات (Screen Inventory) — الخطوة 19

**المشروع:** نظام إدارة التدريب الميداني الجامعي | **النطاق:** MVP | **الواجهة:** عربية RTL  
**المراجع:** `PRD.md`، `docs/UI_UX_REQUIREMENTS.md`، `docs/user-flow.md`، `docs/UX_BLUEPRINT.md`.

> هذا **جرد تخطيطي** للشاشات وليس تصميم واجهات أو كود. مسارات URL مقترحة فقط. يشمل «البيانات» مصادر المعلومات التي تحتاجها الشاشة، لا عقد API نهائيًا. الصفحات المشتركة (لوحة التحكم، الإشعارات، حسابي) تعرض بيانات مختلفة وفق الدور والصلاحية.

## 1. الأولويات وتعريف الحالات

- **Core:** التسجيل والتفعيل، فرص وطلبات التدريب والاعتماد، المتطلبات، الحضور، المتابعة، التقييم.
- **Supporting:** الرسائل، الإشعارات، الحساب، الطلبات الرسمية، الاستثناءات، إدارة الكليات.
- **Future (غير مُدرجة كشاشات):** GPS المستمر، حضور دون اتصال، تقييمات مرحلية متعددة، ميزات خارج PRD.
- **L (Loading):** Skeleton للقوائم/البطاقات، مؤشر إرسال موضعي، تعطيل النقر المكرر.
- **E (Empty):** رسالة عدم وجود بيانات مع إجراء مسموح ومفيد حيث ينطبق.
- **R (Error):** خطأ حقلي/صلاحية/شبكة/تعارض مع استعادة أو إعادة محاولة.
- **S (Success):** تأكيد من الخادم وتحديث الحالة وتوجيه للخطوة التالية.

كل شاشة أدناه تراجع الحالات الأربع **عند انطباقها**؛ «غير منطبق» في بعض شاشات التأكيد أو النماذج لا يعني إنشاء شاشة فراغ مصطنعة. قواعد الاستجابة وإمكانية الوصول فحوص عابرة وليست حالات إضافية.

| K01–K07 | قوائم انتظار/نماذج إدارية | لا طلبات معلقة/مواقع/تخصصات | تعارض/بيانات ناقصة/نطاق كلية | قرار تفعيل/اعتماد/حفظ |
| K08–K13 | متابعة واستثناءات/اطلاع | لا تدريب/حالات | لا تفويض/لا بلاغ قائم؛ منع الوصول | قرار رسمي أو تسجيل اطلاع مدقق |
| A01–A03 | جلب بيانات الكليات | لا كليات | منطقة زمنية ناقصة/تعارض؛ تصحيح | إضافة/تعديل بيانات كلية |

## 4. قواعد مشتركة للتنقل والتحقق

1. **الصلاحيات:** لا تُعرض إجراءات دور آخر، لكن المنع الحقيقي من الخادم؛ بيانات كل كلية معزولة. المسؤول الأعلى لا يرى البيانات التشغيلية افتراضيًا.
2. **حالات الطلب:** مسودة → مراجعة الجهة → مراجعة الكلية → اعتماد أو رفض؛ إلغاء الطالب قبل الاعتماد النهائي فقط. يظهر الخط الزمني وأسباب الرفض.
3. **الحضور:** GPS لحظة التسجيل فقط، اتصال مطلوب، مواقع معتمدة، عدة فترات غير متداخلة في اليوم، وساعات معتمدة فقط تدخل التقدم؛ مسار تصحيح/استثناء مسبب.
4. **التقييم:** مسودة قابلة للتعديل ثم إرسال نهائي واحد؛ لا يُعدل بعد الإرسال؛ تعليق «يحتاج تحسين» إلزامي.
5. **الرسائل:** نص فقط بين أطراف التدريب؛ اطلاع الكلية الاستثنائي مشروط بسبب وبلاغ/طلب قائم وسجل تدقيق.
6. **النتائج:** لا يُعرض نجاح عملية قبل رد الخادم؛ لا تضيع مدخلات النماذج غير الحساسة عند خطأ اتصال.

## 5. فحوص Responsive وAccessibility وRTL (عبر كل الشاشات)

- اختبر عرضًا ضيقًا مثل **390px** وعريضًا مثل **1440px** ولوحيًا؛ هذه قيم اختبار لا Breakpoints إلزامية. الجداول تتحول إلى بطاقات أو تنسيق مناسب، دون إخفاء إجراءات/أسباب مهمة.
- القائمة يمينًا على سطح المكتب وقابلة للطي على الهاتف؛ عناوين عربية واتجاه RTL وأيقونات تنقل مناسبة، مع حفظ اتجاه قراءة البريد والأرقام.
- قِس تباين النص العادي **4.5:1** والكبير **3:1**؛ أظهر Focus واضحًا؛ ادعم لوحة المفاتيح والتسميات البرمجية ورسائل خطأ مرتبطة بالحقول؛ لا تعتمد على اللون وحده.
- راجع حجم أهداف اللمس وفق المنصة والمعيار المستهدف، وأعلن نجاح/خطأ الإجراءات للتقنيات المساعدة.
- حالات التحميل لا تغيّر ترتيب التركيز فجأة، وزر إعادة المحاولة يبقى متاحًا في الشاشات الصغيرة.

## 6. ملاحظات عدم الحسم

- أسماء المسارات والمعرفات أعلاه مقترحة للتوثيق، وليست قرارات هندسية نهائية.
- تفاصيل نصوص الاعتراض وآليات بعض الاستثناءات تُستمد من PRD والسياسات الموثقة عند التنفيذ؛ لا نبتدع مهلًا أو صلاحيات جديدة.
- أي تفاصيل UI غير منصوص عليها في المراجع تبقى اقتراحًا لا شرطًا؛ لا تُضاف شاشات للميزات المستقبلية.
