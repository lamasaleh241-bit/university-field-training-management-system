# تشغيل قاعدة بيانات التطوير محليًا

تنشئ هذه الملفات مخطط PostgreSQL، وتفعّل عزل الصفوف بسياسات RLS، وتضيف بيانات تجريبية. شغّلها في قاعدة محلية فقط؛ بيانات seed وكلمة المرور المشتركة للتجربة وليست آمنة للإنتاج.

## ترتيب الملفات

1. `migrations/001_initial_schema.sql` — الامتداد والأنواع والجداول والمفاتيح والعلاقات والقيود الأساسية.
2. `migrations/002_rls_policies.sql` — أدوار قاعدة البيانات المساعدة، دوال التفويض، triggers وسياسات RLS.
3. `migrations/003_integrity_and_rpc.sql` — التسجيل والتحقق من البريد، تفعيل الحسابات، انتقالات الحالات، قيود تحديث السجلات، وضمانات المحادثات والتقييم والحضور.
4. `seeds/001_demo_data.sql` — كليتان وتخصصاتهما ومتطلباتهما، مستخدمون تجريبيون، الأدوار ومعايير التقييم.

## المتطلبات والتشغيل

تحتاج PostgreSQL 14 أو أحدث و`psql`، وصلاحية محلية لإنشاء امتداد `pgcrypto` وأدوار RLS المساعدة. شغّل الأوامر من جذر المستودع، كـsuperuser محلي أو مستخدم مخول بإنشاء الأدوار والسياسات:

```bash
createdb -U postgres field_training_local
psql -X -v ON_ERROR_STOP=1 -U postgres -d field_training_local -f db/migrations/001_initial_schema.sql
psql -X -v ON_ERROR_STOP=1 -U postgres -d field_training_local -f db/migrations/002_rls_policies.sql
psql -X -v ON_ERROR_STOP=1 -U postgres -d field_training_local -f db/migrations/003_integrity_and_rpc.sql
psql -X -v ON_ERROR_STOP=1 -U postgres -d field_training_local -f db/seeds/001_demo_data.sql
```

استبدل `postgres` باسم حساب الإدارة المحلي عند الحاجة. لا تعِد تشغيل migrations فوق قاعدة سبق تهيئتها؛ أنشئ قاعدة فارغة، أو استخدم أداة migrations لاحقًا لإدارة التحديثات.

## حساب اتصال التطبيق وسياق الكلية

تعرّف migrations الدورين `app_runtime` و`app_policy_owner` دون تسجيل دخول. الأول دور مجموعة للتطبيق بلا `BYPASSRLS`، والثاني يملك بعض دوال السياسات ذات `SECURITY DEFINER` ويملك `BYPASSRLS`؛ يجب ألا يُمنح لأي دور `LOGIN`. أنشئ حساب اتصال محليًا واربطه بدور التطبيق فقط:

```sql
CREATE ROLE field_training_app LOGIN PASSWORD 'غيّر-هذه-كلمة-مرور-محلية';
GRANT app_runtime TO field_training_app;
```

لا ترسل `college_id` أو `user_id` إلى قاعدة البيانات بوصفهما سياقًا موثوقًا. تنشئ migration مفتاح HMAC عشوائيًا في `app_private.context_signing_keys` لا يستطيع دور التطبيق قراءته. استخرجه باتصال إداري آمن مرة واحدة وخزّنه في Secret Manager للخادم فقط:

```sql
SELECT encode(signing_key, 'hex')
FROM app_private.context_signing_keys
WHERE singleton = true;
```

بعد مصادقة المستخدم والتحقق من عضويته، يحسب الخادم HMAC-SHA256 للرسالة النصية `user_uuid:college_uuid`؛ للمسؤول الأعلى تكون الرسالة `user_uuid:`. يحوّل التوقيع إلى lowercase hex، ثم يضبط القيم محليًا داخل معاملة قصيرة:

```sql
BEGIN;
SET LOCAL ROLE app_runtime;
SET LOCAL app.user_id = '30000000-0000-0000-0000-000000000011';
SET LOCAL app.college_id = '10000000-0000-0000-0000-000000000001';
SET LOCAL app.context_signature = '<توقيع HMAC الذي حسبه الخادم>';
SELECT id, name_ar FROM public.colleges ORDER BY name_ar;
COMMIT;
```

لا تمنح المفتاح أو اتصال SQL لمستخدم نهائي. يجب أن يثبت الخادم هوية المستخدم والكلية من جلسة المصادقة قبل توقيع السياق؛ وحماية المفتاح وتدويره مسؤولية إعدادات الخادم.

## التسجيل والتحقق والتفعيل

التسجيل الذاتي ينفذ عبر الدالة المقيدة `app_private.register_user(...)`، وليس بإدخال مباشر إلى `users`. تقبل الدالة فقط أدوار الطالب والمشرف الأكاديمي ومسؤول جهة التدريب، وتتحقق من الكلية والتخصص والحقول اللازمة؛ تكتب الحساب بحالة `pending_activation` وإسناد دور بحالة `pending`. يُرسل التطبيق رسالة تحقق البريد، ويتولى الخادم التحقق من رمزها وتوقيع إثباته بمفتاح HMAC نفسه، ثم يستدعي `app_private.complete_email_verification(user_id, proof)`. صيغة الإثبات هي HMAC-SHA256 للرسالة `email-verified:<user_uuid>:<email-lowercase>` بصيغة lowercase hex. لا يُرسل الرمز أو المفتاح إلى قاعدة البيانات أو المتصفح بصيغة مكشوفة.

مثال استدعاء للطالب (يجب أن يكون `password_hash` ناتجًا عن خدمة المصادقة، لا كلمة المرور الأصلية):

```sql
SELECT app_private.register_user(
  p_college_id    => '10000000-0000-0000-0000-000000000001',
  p_email         => 'student@example.test',
  p_password_hash => '<bcrypt-hash-from-auth-service>',
  p_first_name    => 'اسم',
  p_last_name     => 'العائلة',
  p_role_code     => 'student',
  p_student_number=> 'UNI-12345',
  p_company_name  => NULL,
  p_specialty_id  => '20000000-0000-0000-0000-000000000001',
  p_phone         => NULL
);
```

بعد تحقق البريد، يعتمد مسؤول الكلية الحساب بتحديث `account_status` إلى `active` أو `rejected` وتسجيل `activation_approved_by` و`activation_approved_at`، ثم يفعّل إسناد الدور في `user_roles` ضمن معاملة واحدة. تمنع القيود تفعيل دور لحساب غير نشط أو غير متحقق من بريده. الدوال تخزن `password_hash` فقط؛ توليد الـhash، سياسة كلمة المرور، رسائل التحقق، صلاحية رموزها، استعادة كلمة المرور، تحديد معدل المحاولات وقفل الدخول مسؤولية خدمة المصادقة في التطبيق.

## الحسابات التجريبية

يحتوي seed على كليتين، ولكل كلية مستخدم واحد من أدوار الطالب والمشرف الأكاديمي ومسؤول جهة التدريب ومسؤول الكلية، إضافة إلى مسؤول أعلى واحد بلا كلية. كل الحسابات مفعّلة ومتحقق من بريدها محليًا للتسهيل. كلمة المرور المشتركة هي `LocalDemo!2026`، والبريد هو اسم الدخول ضمن النطاق `.example.test`. غيّرها وأزل بيانات seed قبل أي نشر أو بيئة مشتركة. قيم متطلبات التخصص أمثلة اختبار وليست متطلبات معتمدة.

## ما تضمنه قاعدة البيانات وما يبقى في التطبيق

- RLS يطبّق سياق الكلية والدور، مع حصر القراءة الاستثنائية للمحادثة ببلاغ أو طلب قائم وسجل تدقيق مطابق له. يمكن استدعاء `app_private.log_exceptional_conversation_access(conversation_id, case_type, case_id, reason)`؛ وتكون `case_type` إما `dispute` أو `official_request`. يجب استدعاء الدالة قبل قراءة الرسائل ضمن السياق نفسه.
- تُسجّل انتقالات حالة الطلب تلقائيًا، ولا يُسمح للتطبيق بإدخال سجل تاريخ عشوائي. عدد الطلبات النشطة محدود بطلب واحد لكل طالب؛ يسمح بتعديل المسودة، وإرسالها إذا ظلت الفرصة مؤهلة، أو إلغاء الطلب النشط.
- المقعد يُحجز عند اعتماد الكلية النهائي فقط، مع قفل على الفرصة لمنع تجاوز عدد المقاعد بالتزامن. نفّذ اعتماد الطلب داخل معاملة قصيرة ومستوى عزل متوافق مع منطق القفل في migration.
- اعتماد موقع التدريب ونطاق GPS ودقة الإحداثيات، صلاحية الموقع أثناء تسجيل البصمة، التحقق من حد الـ100 متر ودقة GPS، المنطقة الزمنية عند تحويل التوقيت إلى يوم كلية، والتحقق من الملف المرفوع ومحتواه وحجمه، تظل مسؤوليات خدمة التطبيق. تخزن القاعدة البيانات والأدلة، لكنها لا تستبدل التحقق الجغرافي أو تخزين الملفات الآمن.
- الاعتماد اليومي للحضور يحتسب `approved_minutes` من وقتي الحضور والانصراف ويطبّق سقف ساعات التخصص؛ لا يخصم الاستراحات. على التطبيق تنفيذ أثر قرار طلب التصحيح المقبول على سجل الحضور، وإظهار أسباب رفض التصحيح/الاستثناء.
- إنهاء التدريب المبكر يتطلب طلبًا رسميًا معتمدًا، وتغيير المشرف يتطلب طلبًا رسميًا معتمدًا وإسنادًا جديدًا. إسناد المشرف الجديد يحدّث المشرف الحالي في صف التدريب تلقائيًا.
- لا يفرض المخطط حاليًا سجل حضور واحدًا فقط لكل طالب في اليوم؛ يلزم حسم ما إذا كانت الورديات المتعددة ممكنة قبل إضافة قيد فريد على `(training_id, attendance_date)`. كذلك يحتاج استثناء إنهاء التدريب دون تقييم إلى تمثيل بيانات مستقل إذا أُريد توثيقه.
- دورة اكتمال التدريب النهائية وإغلاقه تلقائيًا بعد بلوغ متطلبات الساعات/المدة، التعامل مع العمل في العطل، وتعطيل الحسابات النشطة (`suspended`) ليست إجراءات آلية مكتملة في هذه migrations؛ يلزم تنفيذ قواعدها في التطبيق أو اعتماد قرارات إضافية قبل نشرها.
- هذه migrations نقطة بداية قابلة للمراجعة، وليست بديلًا عن مراجعة أمنية واختبارات سلبية لعزل الكليات، واختبارات تزامن الاعتماد، قبل النشر.
